# Servidor de conta e sincronização — plano de implementação

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** o servidor de verdade para conta e sincronização, rodando na VPS em
`https://api.excalisidian.com`, cumprindo os contratos que o app já tem. A IA própria fica para
o plano seguinte.

**Architecture:** pasta `servidor/` neste repositório, pacote Node próprio. Fastify + SQLite.
As regras do diário vêm de `src/sync/nucleoServidorSync.ts` (o mesmo núcleo do servidor falso),
com um armazenamento novo (SQLite + arquivos). Empacotado com esbuild num arquivo só; na VPS roda
como serviço `systemd` atrás do Caddy.

**Tech Stack:** Node 22, TypeScript, Fastify 5, better-sqlite3, esbuild, vitest; na VPS: Caddy,
ufw, systemd.

**Spec:** `docs/18-servidor.md` (normativo), `docs/17-sincronizacao.md` §9/§9.1,
`src/conta/ServicoContaHttp.ts`, `src/sync/ServicoSyncHttp.ts`, ADR-38, ADR-39.

## Global Constraints

- Português do Brasil em nomes e comentários.
- **A prova da verdade são os clientes do app:** os testes do servidor rodam `ServicoContaHttp`
  e `ServicoSyncHttp` de verdade contra o servidor em processo (via `fastify.inject` adaptado
  para a assinatura de `fetch`), e um teste roda o motor de sincronização (`executarCiclo`) com
  dois computadores contra o servidor. Se o cliente e o servidor discordarem, o teste pega.
- Testes antes, vistos falhando. O vitest da raiz não roda os testes de `servidor/` (e
  vice-versa) — cada pacote tem o seu.
- Logs nunca contêm e-mail, token, prova, corpo, id de vault (doc 18 §3).
- **Guarda de higiene de commit:** trabalho não commitado do usuário em `src/editor/`,
  `src/layout/AbaDocumento.tsx`, glossário e documentos não rastreados em `docs/superpowers/`.
  Não toque. Commit com pathspec (`git add -- <novos>`, `git commit -m "..." -- <caminhos>`);
  nunca `git add -A`, `git add .`, `git commit -a`; `index.lock`: espere e tente de novo.
- Nenhuma tarefa acessa a VPS. Só a Task 7, pelo orquestrador, com autorização do dono do produto.

### Task 4: Conta e sessões (sonnet, medium)

- [ ] Rotas exatamente as de `ServicoContaHttp`: criar (`POST /contas`), entrar
  (`POST /sessoes`), renovar (`POST /sessoes/renovar`, Bearer), sair (`DELETE /sessoes`).
  Corpo `{ email, provaDeIdentidade, kdf }`; resposta `Sessao` como o app espera.
  `kdf` desconhecido → 400.
- [ ] scrypt da prova com sal por conta; comparação em tempo constante. Mesmo 401 para e-mail
  inexistente e prova errada — e o mesmo tempo aproximado (calcule o scrypt contra um sal falso
  quando o e-mail não existe).
- [ ] Sessões: token 32 bytes base64url, banco guarda SHA-256, 30 dias, renovar troca o token.
- [ ] Limite de tentativas (doc 18 §3) → 429.
- [ ] Testes com o `ServicoContaHttp` real contra o servidor em processo: criar, entrar, renovar,
  sair, e-mail repetido, prova errada, e-mail inexistente (mesma resposta), token velho depois de
  renovar é recusado, limite de tentativas. E um teste de que o banco não contém a prova nem o
  token em texto.
- [ ] Commit: `feat(servidor): conta e sessoes`.
